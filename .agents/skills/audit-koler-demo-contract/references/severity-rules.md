<overview>
Severity отражает влияние расхождения на безопасность и воспроизводимость
стенда, а не размер diff.
</overview>

<levels>
<severity name="P0">
Блокирует запуск или допускает опасное внешнее действие: отсутствующий
обязательный DB/R2 binding, несовместимый persisted contract, реальная
отправка/резерв вопреки guardrail, утечка секрета, необратимая мутация.

Результат: `FAIL`, exit code 1. Вебинар или релиз блокируется.
</severity>

<severity name="P1">
Меняет наблюдаемое решение или делает главный сценарий недостоверным:
неверная роль модели, расходящийся `AgentResult`, неверные числа/маршрут,
документация, противоречащая runtime, неподтверждённый внешний факт,
timeout/lease, допускающий повторную обработку.

Результат: `FAIL`, exit code 1. Нужно согласовать или исправить до показа.
</severity>

<severity name="P2">
Не меняет текущий результат, но ослабляет доказательство или поддержку:
отсутствующий executable regression, неполный dependency note, неоднозначная
операторская формулировка без прямого противоречия.

Результат: `PASS WITH P2`, exit code 0, если P0/P1 отсутствуют.
</severity>
</levels>

<classification_rules>
- Несколько слабых сигналов не повышают severity автоматически.
- Missing file у core runtime — P0; missing operator document — P1 или P2 по
  наблюдаемому влиянию.
- Документированное ограничение не является дефектом само по себе.
- Потенциальная гонка получает P1, если рассчитанный worst case превышает
  lease и job-specific renewal отсутствует.
- Findings объединяются по одному claim, чтобы десяток отсутствующих полей не
  создавал десяток одинаковых строк.
- Каждая строка findings обязана содержать точное canonical и conflict
  location. Для отсутствующего файла используется ожидаемое `file:1`.
</classification_rules>

<exit_policy>
- Есть хотя бы один P0/P1: exit 1.
- Есть только P2 или findings нет: exit 0.
- Некорректные CLI arguments: exit 2.
- Ошибка чтения обязательного core-файла оформляется P0, а не скрывается как
  exception без отчёта.
</exit_policy>
