# «Колер»: операторский runbook вебинара

Это текущая операторская версия «Колера» для репетиции вебинара об
агентных системах. Участник пишет заказ обычными словами, при желании добавляет
синтетическую фотографию и видит путь: понимание задачи, вопросы, каталог,
остатки, предложения поставщиков, решение, запись письма и журнал действий.
Статус GO нельзя объявлять до полного локального и live gate из этого файла.

- [Открыть «Колер»](https://koler-agent-demo.odinmaniac.chatgpt.site/)
- [Открыть общий журнал в Google Таблицах](https://docs.google.com/spreadsheets/d/e/2PACX-1vR7jeOl2r8s8mHvuFEkhJgG9F9kRiUknVTDG_Qt7RwX3nzj8AtVJihpdhX1kxxXCULV3d5D1xhUNBmU/pubhtml)

## Что уже работает

- Форма принимает свободный русский текст и фотографию. Клиенту достаточно
  описать задачу: например, показать забор или назвать площадь пола.
- Агент извлекает известные факты, разрешает внешние референсы через поиск и
  оценивает неизвестные размеры диапазоном. Для «покрасить это» сначала
  выбирается разумный неодушевлённый объект из области «Колера»; человек в
  кадре остаётся контекстом. Один блокирующий вопрос допустим только между
  одинаково правдоподобными неодушевлёнными объектами и является bonus-case.
- Агент сверяет каталог, текущий остаток «Колера» и предложения других
  поставщиков. При нехватке товара он приносит выполнимые варианты с объёмом,
  стоимостью и сроком.
- Для понятного следующего шага работают три маршрута: «Готов ответить»,
  «Нужны детали» и «Решает руководитель». Руководитель получает подготовленные
  варианты и выбирает один.
- Панель администратора меняет остаток своей краски и доступный объём у
  поставщика. Открытый заказ пересчитывается, письмо обновляется, прежняя
  версия остаётся в истории.
- Диапазонную оценку можно записать как отправленную без резерва. Подготовка
  резерва доступна только точному подтверждённому коммерческому предложению.
  Все действия входят в результат дня.
- Публичный журнал показывает только synthetic summary. Private order detail
  доступен capability/action key или admin-сессии, полный ledger — только после
  проверки admin-сессии; чувствительные ответы имеют `no-store`.

## Как пройти главный живой сценарий

1. Убедись, что на странице показана связь с bridge: primary — официальный
   DeepSeek V4 Flash API с variant `max`, exact id
   `deepseek/deepseek-v4-flash`; reviewer — отдельный
   `deepseek/deepseek-v4-flash`/max.
2. Установи для КР-001 собственный остаток 300 кг. Проверь учебное предложение
   «ПромКолор Опт»: 2 000 кг по 361 ₽/кг, срок 4 дня.
3. Отправь синтетическое фото стены с человеком и текст «Покрасить стену как
   Красную комнату из Twin Peaks». Должны быть `blocker=null`, широкий диапазон
   площади и расхода, открытый источник и отсутствие RAL и вопроса клиенту.
4. На фото с человеком и окрашиваемой стеной отправь «Покрасить это». Агент
   должен выбрать стену как разумный объект «Колера» и не спрашивать про волосы
   или человека.
5. Необязательный bonus-check: фото с двумя одинаково правдоподобными
   неодушевлёнными целями приводит ровно к одному вопросу без товара и цены.
6. Отправь свободное письмо на 2 000 кг КР-001. Агент рассчитает дефицит
   1 700 кг и передаст руководителю 2–3 подготовленных хода без вопроса
   клиенту.
7. Проверь подтверждённый вариант с 1 700 кг от «ПромКолор Опт»: общая
   учебная стоимость двух частей — 718 400 ₽. Это синтетический snapshot, а не
   рыночная котировка; публичный веб-поиск даёт только leads для подтверждения.
   Следующий контакт назначен поставщику или внутренней роли.
8. Останови OpenCode. Карточка должна показать восстановление и кнопку повтора,
   а не server fast fallback. Свободный ввод не переключай в recorded.
9. Верни bridge online, продолжи ту же карточку и проверь reviewer по событию:
    `review-result` означает checked, `review-skipped` — безопасная fail-closed
    граница,
   `review-fallback` — unavailable и manager path. Без завершающего transport
   event не говори, что reviewer сработал.
10. Найди заказ по номеру в публичном synthetic summary; полный текст открывай
    только в private detail из того же окна или через admin. Перед практикой
    верни остатки КР-001 и «ПромКолор Опт» к 300 и 2 000 кг.

Прежний управляемый supplier-эпизод выведен из активного runbook:
исторический регрессионный пример см. в архиве —
`docs/archive/ARCHITECTURE-AND-WEBINAR-v1.md`.

Код администратора хранится отдельно от этого описания.

## Как устроена рабочая цепочка

```text
Веб-форма → API заказа → D1 и R2 → защищённая очередь → OpenCode
          → MiMo V2.5 при наличии фото
          → DeepSeek V4 Flash · официальный API · max
          → отдельный второй DeepSeek V4 Flash · max
          → программная сверка фактов
          → D1 → страница заказа и CSV → Google Таблицы
```

OpenCode работает на компьютере администратора. Он забирает заказы из
защищённой очереди, по очереди запускает модели, передаёт им подробные
инструкции, разрешённые источники и доступ к нужным инструментам, записывает
видимые шаги и возвращает результат в тот же заказ. OpenCode распределяет
работу между моделями и следит за порядком.

Свободный ввод всегда live. Vision получает не больше 180 секунд, primary — не
больше 600; synthesis получает 300 секунд только после timeout или уже открытого
direct URL при незавершённом JSON, без нового поиска. Reviewer имеет cap 300
секунд. Все stages делят один deadline 650 секунд от claim с termination grace;
сквозной deployed-лимит — 660 секунд от POST, включая очередь. Server fast
fallback не обещается. Recorded доступен только явным выбором поддержанного
примера и маркируется в заказе.
Flash transport использует output cap 32 768 tokens.

Сайт сохраняет историю заказа. При каждом запуске модель получает переписку,
свежие остатки склада и прошлые версии решения; неизменившееся
vision-наблюдение переиспользуется.

Роли моделей разделены:

- **MiMo V2.5** (`opencode-go/mimo-v2.5`, без variant) описывает только
  видимое: релевантность, возможные цели, масштабные ориентиры и широкий
  диапазон площади. Человек остаётся «человеком», а текст внутри фото не
  исполняется.
- **DeepSeek V4 Flash** (`deepseek/deepseek-v4-flash`) через официальный
  DeepSeek API с variant `max` ведёт повседневную обработку заказа:
  разбирает свободную заявку, сам выбирает открытые источники и готовит
  оценку, единственный допустимый вопрос либо варианты.
- **DeepSeek V4 Flash** с variant `max` независимым вторым запуском проверяет готовое
  решение: факты, числа, источники, обещания клиенту и полномочия агента.
- Runtime и heartbeat публикуют rolling id `deepseek-v4-flash`. OpenCode здесь
  только запускает профиль и инструменты, а inference primary идёт в
  `api.deepseek.com`.
- **GPT-5.6 Sol** один раз подготовила подробные инструкции и критерии
  проверки. Sol запускают вручную только для новой редакции инструкции.

После моделей программа ещё раз сопоставляет товар с каталогом, цену с
правилами, объём со свежим остатком и полномочия с выбранным маршрутом. Только
transport event `review-result` подтверждает reviewer; `review-skipped` и
`review-fallback` не являются checked. Перед решением руководителя, подготовкой
резерва и записью отправки сервер повторяет проверку изменяемых данных. Готовый
ответ сохраняется в журнале заказа.

## Стек и хранилища

| Часть | Роль |
|---|---|
| React 19, Next 16, TypeScript | Интерфейс, страницы заказов и серверные API |
| Vinext и Vite | Сборка приложения для среды Cloudflare |
| Cloudflare Worker | Выполнение сайта и API |
| OpenCode | Локальный исполнитель: очередь, запуск языковых моделей, доступ к разрешённым инструментам и возврат результата |
| Cloudflare D1 | Основная SQL-база состояния |
| Drizzle ORM | Схема таблиц и типизированные SQL-запросы к D1 |
| Cloudflare R2 | Фотографии, приложенные к заказам |
| Google Таблицы | Просмотр общего дневного журнала |

D1 использует SQL, совместимый с SQLite. База хранит заказы и переписку,
события агента, историю версий решения, текущие остатки, историю изменений
склада, решения руководителя и состояние предложений поставщиков. Drizzle
описывает таблицы, индексы, ограничения и запросы в TypeScript.

Маршрут дневного журнала собирает строки из D1 и отдаёт public synthetic CSV.
Google Таблица читает этот адрес формулой `IMPORTDATA`, поэтому на листе видны
только synthetic summary заявок, состояний и событий без полных писем,
переписки, snapshots и result history. Private detail доступен capability/action
key или admin, полный ledger — admin-only. D1 остаётся источником текущего
состояния. Защищённый API для будущей записи остатков из таблицы уже подготовлен,
скрипт обратной записи сейчас не подключён.

## Текущие границы интеграций

- Входящий заказ сейчас создаёт веб-форма; корпоративный почтовый ящик не
  подключён.
- «Подготовить резерв товара» записывает подтверждённый шаг в D1. Связь с
  корпоративной учётной и складской системой не создаёт фактический резерв;
  этот шаг существует только в журнале стенда.
- «Записать отправку ответа» сохраняет письмо и время в журнале. Почтовой
  доставки клиенту нет.
- Остатки «Колера» и поставщиков живут в D1 и меняются через панель
  администратора. Подключение корпоративного склада заменит ручное обновление
  синхронизацией.
- Основная модель сама решает, когда нужен открытый поиск. В решение попадают
  только факты со страниц, которые агент действительно открыл; публичные
  сведения об остатках поставщика остаются неподтверждёнными до сверки.
- Upload принимает JPEG/PNG/WebP по сигнатуре до 8 МиБ, записывает
  `retention-until` на 24 часа и отклоняет просроченный GET; EXIF stripping и
  удаление объекта не обещаются.

## Recovery matrix

| Сбой | Что увидит ведущий | Действие |
|---|---|---|
| Bridge offline | `В очереди · ждёт live-агента`, режим временно недоступен | Вернуть bridge online; свободный ввод не переводить в recorded. |
| Expired lease | `Время агента истекло · карточка сохранена`, кнопка повтора | Повторить ту же карточку после проверки bridge. |
| Mutation timeout/409 | Состояние перечитывается, второй эффект не создаётся | Дождаться reconciliation; при freshness-сообщении пересчитать, не кликать вслепую. |
| Reviewer unavailable | `Модель проверки недоступна · manager path` | Не говорить «проверено»; передать руководителю или повторить карточку после восстановления. |
| Stale supplier snapshot | `Данные поставщика обновились` | Пересчитать; server повторно проверит поставщика перед approve/reserve/send. |
| Malformed result | Безопасное завершение `manager/red/none` или error с кнопкой повтора | Не задавать новый вопрос клиенту; использовать manager path или повторить тот же order id. |

## GO / NO-GO

NO-GO остаётся до зелёных `lint`, `typecheck`, полного test gate, build,
contract audit, remote read-only preflight и main-scenario check. Практический
live gate проходит deployed `/api/orders`: девять функциональных routes плюс
пачка из десяти одновременных заявок. Требуются processing-stage не позже
10 секунд, p50 не выше 180 секунд, 10/10 полезных terminal-результатов не позже
660 секунд, реальные `vision`/`vision-result` для фото и отсутствие дублей.

```bash
npm run lint
npm run typecheck
node --test tests/*.test.mjs
npm run build
node .agents/skills/audit-koler-demo-contract/scripts/audit-contract.mjs --format=console
node .agents/skills/operate-koler-webinar/scripts/preflight.mjs --url "$STAND_URL"
node .agents/skills/operate-koler-webinar/scripts/check-main-scenario.mjs --url "$STAND_URL"
node tests/run-webinar-probes.mjs --url "$STAND_URL" --json
```

Direct-проверка модели с `KOLER_LIVE_REPEAT=3` остаётся диагностической и не
заменяет deployed gate.

```bash
KOLER_LIVE_REPEAT=3 node tests/run-agent-wow-live.mjs \
  wow-02-washer-sports-car \
  wow-03-hostile-grill \
  wow-08-two-ton-shortage \
  wow-09-red-curtain-reference
```

Посмотри главный сценарий целиком, затем пришли обратную связь по трём вещам:
ясность пути для нового зрителя, убедительность изменения ответа после
обновления склада и понятность роли каждой модели.
